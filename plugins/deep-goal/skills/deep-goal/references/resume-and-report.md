# Resume & final run report

The conductor's two bookends: **re-entry** (§ 1 - crash-safe resume from `00-Manifest/pipeline.md`, contract rows #3 and #8) and the **final run report** (§ 2 - the completion artifact that surfaces everything autonomous mode decided alone, contract row #6). `references/conductor.md` § 7 is the summary; this file is the spec. Everything here reads the state Phases 4-5 already persist - `pipeline.md` (`templates/pipeline.md`), `findings.json`, the plan's Assumptions section - and **never re-derives what the header recorded** (except for the exceptions in `references/resume-and-report.md` § 1.3).

## 1. Re-entry protocol

### 1.1 Detection - the FIRST launch check

Before anything else in the launch sequence (`references/conductor.md` § 1 - before rigor resolution, before the handshake), check for prior state:

- **Invocation targets an effort** (an effort named in the invocation - "resume the `<slug>` effort" - or a goal whose derived slug matches an existing effort dir; deep-goal has no `--effort` flag of its own - that flag belongs to the *dispatched* `deep-plan`; a `--from-plan=<path>` targets that path's effort) **whose `00-Manifest/pipeline.md` exists** → re-entry (§ 1.2) - never adoption (`conductor.md` § 1c).
- **Bare resume invocation** ("resume deep-goal", "continue the run", re-invoking after a pause notification) → scan `.deep-skills/*/00-Manifest/pipeline.md` for **open runs**: any dispatch record not `complete`, or all records `complete` with a HALT Blockers row or no `run-report.md` yet. Exactly one open run → target it. Several → the re-entry question carries one resume option per open run (previews per § 1.2). None → say so; nothing to resume.
- **No prior pipeline.md** for the targeted effort → not a re-entry; the normal launch sequence continues.
- **`--dry-run` never re-enters** - it prints the preview and stops, touching nothing, prior state or not.

A run that already completed cleanly (all records `complete`, `run-report.md` written, no HALT row) is not resumed and not archived unprompted: announce it is done, point at `00-Manifest/run-report.md`, and ask nothing further unless the user asks for a fresh run.

### 1.2 The re-entry question - one, self-contained

Once § 1.3 rule 1's version re-check has passed (it runs first and may refuse before any question), announce prior state and offer **resume / fresh** as **one structured question** (host-affordances: native structured-question tool, numbered-list chat fallback). It is **self-contained**: each option's description/preview (**≤ 15 lines** - hosts truncate beyond that) carries the prior-state summary a decision needs, never between-tool-call prose - rigor + source, **max + source**, **base** - `base <id>` when the current session model matches the header, **`base was <id>, now <id>`** when it differs (inline stages from here on run on the new one) - records complete/total, the resume point (first non-`complete` record, its status, and what resuming does to it per § 1.3), any Blockers rows, budget state (ceiling · running total · paused boundary), unfired gates, worktree path, spend so far. On a legacy header (written by deep-goal < 0.3.0, § 1.3), max and base show as `(resume backfill)`. Trim the completed-stages list first when squeezing under 15 lines.

- **Resume** (recommended default) - continue per § 1.3. On a **budget-paused** run the resume options also cover the ceiling: keep it (warn: still crossed → it pauses again immediately), raise it, or remove it - either as option variants or honoring a ceiling stated in the invocation itself ("resume with a 1m budget"); any change is logged as a Budget events row (`ceiling raised to ~<band>` / `ceiling removed`) before the boundary re-check.
- **Start fresh** - archive `00-Manifest/pipeline.md` to **`00-Manifest/pipeline-archived-<n>.md`**, where `<n>` = 1 + the highest existing archive number (`pipeline-archived-1.md` first; no timestamps), then fall through to the normal launch sequence from the top (rigor and max re-resolved - asked again only if the invocation doesn't state them - models re-resolved against the current session, handshake re-run, a new launch card, a new pipeline.md written after Launch). Fresh archives **only the pipeline state** - the manifest, plan, and stage artifacts remain, and the new run re-plans and re-runs stages over them per each skill's own semantics (re-reviews append findings; bugfix appends round dirs) - the fresh option's preview must say so. The relaunch's new pipeline.md records a **fresh artifact baseline** over whatever survives (`conductor.md` § 4), so the new run's advance tests judge its own work: the archived run's artifacts can neither pass a stage the new run did not run nor fail one it ran (a round-1 review appending over the old findings.json is judged round-aware against that baseline, never by "statuses all `open`").
- **Loop-halt runs** (all records `complete` but the run halted via a HALT Blockers row from the convergence machinery - cap-1 certificate FAIL, or cap-≥2 convergence failure): the resume choice splits into two options - **one more round** (triage → bugfix → re-review at the level's own entry; the human's explicit choice overrides the cap **once per re-invocation**, recorded in the new records' Notes as `resume: user authorized round N past cap/halt`) or **exit to docs** (proceed to the remaining map stages, all non-`fixed` findings reported as residuals). Both stay inside the same question.

### 1.3 The resume walk

**Honor persisted state - re-read, never re-derive.** The pipeline.md header and Stage list table are authoritative: rigor + the resolved stage list (never re-resolve the map), **max** (never re-asked) and **base** (never re-derived - only compared with the current session model for the preview), the Stage list's planned/actual models (never re-resolve the model map - an override edited since launch applies to the next fresh run, not this one (unless the snapshot was lost - below), and every stage keeps reading the frozen `00-Manifest/model-map.resolved.json` - dispatched stages through their briefing, a re-opened inline planning window through the frozen-map clause (the `plan` row below; `conductor.md` § 2) - so leads and helper fleets stay on the launch map; resume never rewrites it), gates, budget ceiling, worktree path, the artifact baseline (never re-snapshot - a resume that re-recorded it would misread this run's own pre-crash work as pre-existing; the one standing exception is the worktree re-record of the `docs/ai-map/ (code tree)` row, `loop-and-budget.md` § 5). **The deep-skills location is re-discovered on every resume** (`conductor.md` § 1a, read-only, before the re-entry question). It is an install pointer, not run state: install caches are version-pinned, and a superseded version's dir can survive an upgrade, so the recorded path may still exist while pointing at an install that is no longer current. When the location differs from the header, update the header's `deep-skills:` path (written once Resume is chosen) and use it for `{skill_path}` and the shipped model map from then on. Exception - a persisted **path that no longer exists on disk**: the worktree path gone → recreate the same tree from its recorded branch (`git worktree add <recorded-path> deep-goal/<effort>` - the commits live in the branch, not the tree), still never a *second* worktree - and re-record the `docs/ai-map/ (code tree)` baseline row from the fresh checkout (`loop-and-budget.md` § 5: recreation resets every mtime, so a stale row would let a died docs stage false-pass; the re-record errs only toward one safe re-dispatch of deep-docs `--refresh`); the frozen `00-Manifest/model-map.resolved.json` gone → re-write it once from the **current** sources: the shipped map at the re-discovered deep-skills location, merged with the repo override as it stands now (load + merge + validate per `conductor.md` § Model resolution step 1 - an invalid override refuses as at launch), and log a Notes line on the resume-point record (`model-map.resolved.json missing - re-written from current sources (may differ from the launch map)`).

**Resume's exceptions to never-re-derive** (the only place they are listed):

- (a) **deep-skills location re-discovery**, every resume (above);
- (b) **version re-check**, every resume (rule 1 below);
- (c) **legacy back-fill**, once, of a pre-0.3.0 header (rule 2 below);
- (d) **path-gone recoveries** (above): the worktree recreated from its branch plus its `docs/ai-map/ (code tree)` baseline-row re-record, and the frozen model-map snapshot re-written from current sources.

**Re-validate against this deep-goal.** The header may have been written by an older deep-goal that resolved less state, or checked it against a lower requirement. Two rules close that gap:

1. **Version re-check, every resume.** Before the re-entry question is asked, re-read `version` from the `plugin.json` at the location just re-discovered (above) and re-run SKILL.md § Launch step 2's comparison against **this** deep-goal's minimum (0.3.0). Below it → refuse exactly as at launch (name the installed version and the required minimum, suggest updating; dispatch nothing, write nothing - the pipeline.md stays the resume point). Passes or warns → overwrite the header's `deep-skills:` version outcome with the fresh result (written once Resume is chosen; Fresh re-runs the handshake anyway). The persisted outcome is a record of the last check, never a licence to skip it.
2. **Legacy header back-fill, once.** A header written by deep-goal < 0.3.0 lacks the `**Max:**` line, the `**Base:**` line, and the Stage-list `Model` column (and its invocations lack `--max`); **any** of the three missing marks it legacy, and only the missing pieces are back-filled (so a crash mid-back-fill finishes it, never redoes a piece already written). Each is resolved **once**, as at launch, then persisted and never re-derived again: max from the invocation if it states one, else asked as a second question **in the same structured question set as the re-entry question** (one tool call; recommended answer = base's tier; previews per SKILL.md § Rigor resolution / the model-level previews of `conductor.md` § 1 step 2) - when the question offers several open runs (§ 1.1), ask it instead as one follow-up question once a legacy run's Resume is chosen; base = the current session model (`conductor.md` § Model resolution step 2); planned models resolved for every **non-`complete`** stage per `conductor.md` § Model resolution, over a merged map loaded then and frozen as `00-Manifest/model-map.resolved.json` (`conductor.md` § 1 step 8 - a legacy run has none). Write the `**Max:**` header line (source `asked` / `flag` / `default` plus ` (resume backfill)`, and its `models from` slot naming the frozen file and its sources) and the `**Base:**` line (plus ` (resume backfill - resuming session)`), and add the Stage list `Model` column: non-`complete` rows get their launch-rule rendering - planned `<tier>: <model-id>` for dispatched stages, `your session: <current id> (inline)` for interactive planning, `your session: <current id> (inline-led)` on a host without background agents - (overwritten at dispatch with the model that actually ran, from the agent's model report - `references/model-map.md` § Host binding); `complete` rows get `unknown (pre-0.3.0 run)`, never a guessed model. Invocations gain `--max=<x>` when re-rendered at dispatch (`conductor.md` § 3 step 2 already renders it from the header). The § 1.2 preview shows `max: <to be chosen | x> (resume backfill)` and `base <id> (resume backfill)`. Nothing is written until Resume is chosen; a max answered here followed by **Start fresh** counts as stated in the invocation for the relaunch (never asked twice).

**Resume with a changed session model:** the persisted max still governs every dispatched stage (their planned models stand, with try-and-fall-back at dispatch as usual); **inline** stages - interactive planning, and every stage lead on a host without background agents - run on the **current** session model, because nothing else is possible; each records the model it actually ran on (`your session: <current id> (inline)`), so the run report names, per stage, the model that ran. The header's Base line is not rewritten - it records the launch session.

**Adopted plan records are never re-tested.** A `--from-plan` run's plan record is `complete` from Launch (`conductor.md` § 1c); resume skips it like any complete record and never re-judges the adopted plan.md - even if it was edited since.

**Resume point = the first dispatch record that is not `complete`** (`pending`, `in-flight`, or `halted` - inline stages have records too, so a crash during mvp/prod planning resumes correctly). Action by what is found:

| Found | Meaning | Resume action |
|---|---|---|
| `pending` record | stopped at a boundary - crash, budget pause, or gate stop before dispatch | **Re-enter AT that boundary**, running its checks in the Phase-5 order (`loop-and-budget.md` § 6): the loop checks first when the boundary is inside the review→fix loop - including the **empty-set short-circuit** (§ 1.5: a pending triage with zero `open` findings, or a pending bugfix with zero `accepted`-and-unfixed findings, is skipped, never dispatched); then the budget check, against the current - possibly just-raised - ceiling (still crossed → pause again, notify with a raise hint); then the gate check - a gate set before this stage **re-fires** unless the record's Notes already show `gate: approved`; then mark `in-flight` and dispatch normally. |
| `in-flight`, artifacts **complete** (advance test passes) | the stage finished; the crash hit between finish and record update | **The idempotency rule:** mark the record `complete` (advance-test result; Notes `resume: found complete, not re-dispatched`) and advance to the next boundary. Never re-dispatch. Overwrite the stage's Model cell, since no model report exists. On a header that was back-filled this resume (pre-0.3.0 launch) → `unknown (pre-0.3.0 run)`. Otherwise → `<planned/attempted id> (unverified - resumed, model not observed)`. |
| `in-flight`, artifacts **incomplete** | the stage died mid-flight | **Re-dispatch the same stage once** (same briefing, re-rendered from the persisted header + map entry), leaning on the skill's internal resume (table below). Fails its advance test again → HALT-class blocker per `conductor.md` § 4. |
| `halted` record | the stage failed its advance test / hit a blocker; the human has since intervened (their re-invocation says so) | Re-dispatch that stage; its internal resume picks up from what stands (e.g. deep-implement re-entering at the blocked phase after the human unblocked it). The Blockers row stays as history; the new outcome writes a fresh record completion. |
| all `complete` + HALT Blockers row (loop halt) | the *run* halted at the loop exit, not a stage | Per the re-entry question's loop-halt options (§ 1.2): one more round, or exit to docs. |
| all `complete`, no HALT row, **no `run-report.md`** | crash between the last stage and the report | Run the completion sequence (§ 2.1) - resume's cheapest case. |

**Round-aware, always:** when the record in question is a review round ≥ 2, "artifacts complete" is **never bare artifact existence** (vacuously true from round 2) - it is the **round-aware test** against the snapshot in that round's Review loop row (`loop-and-budget.md` § 1.2): fresh CR ids or status changes AND an updated `reviewed` date / mtimes. A crash mid-re-review therefore re-dispatches; it never marks an un-run round complete. Round 1 over a pre-existing `findings.json` is judged the same way, with the pipeline.md Artifact baseline as the snapshot (`conductor.md` § 4).

**What each core skill's internal resume gives you** (why one re-dispatch is safe):

| Re-dispatched stage | Internal resume mechanism |
|---|---|
| `plan` (autonomous) | none needed - `plan.md` is the only output; the planner re-runs clean, nothing partial to reconcile |
| `plan` (interactive, mvp/prod) | not a dispatch: **re-open the inline planning window** - the user re-invoking *is* the interactivity; run `deep-plan <goal> --rounds=<n> --effort=<slug> --confirmed --max=<x>` inline + the frozen-map clause (`conductor.md` § 2: tell deep-plan its model map is `<invocation-repo root>/.deep-skills/<slug>/00-Manifest/model-map.resolved.json`, absolute, in place of the shipped map and any override) - goal, slug and max from the header, `--rounds`/columbo from the map entry (the goal and name were settled on the launch card - no restate, no re-confirmation) |
| `plan-review` | re-runs whole (single review artifact; rewrite is safe) |
| `implement` | plan.md § Phase Summaries - completed phases stand; it re-enters at the first unfinished phase, no duplicate commits |
| `code-review` (review) | re-runs the round; report/certificate are rewritten for the round, findings append per the round contract |
| `code-review (triage)` | naturally idempotent - only `open` findings get flipped; prior statuses are preserved by contract |
| `bugfix` | `06-Bug-Fix/round-N/scope.json` - the round's scope is fixed at intake; re-entry resumes the round's remaining clusters |
| `docs` | deep-docs `--refresh` semantics - incremental over the existing `docs/ai-map/` |

**Double-dispatch guard, re-entry edition:** within a live session, `conductor.md` § 3's guard *announces* an in-flight stage rather than dispatching beside it. On re-entry the human's re-invocation is the evidence the prior conductor died - so the question announces the in-flight record (and whether its artifacts check out), and choosing Resume either completes it (idempotency row) or re-dispatches it (died mid-flight row). Exactly one re-dispatch per resume per stage; a stage is never dispatched while another record is `in-flight`.

**What resume never does** (except for the exceptions in `references/resume-and-report.md` § 1.3)**:** re-ask rigor or max · re-derive base or re-resolve models · re-derive the header · archive anything (that is fresh's job) · rewrite a `complete` record · re-fire an approved gate · create a second worktree or effort dir · dispatch past a boundary whose checks fail.

## 2. The final run report

The report is the run's accountability artifact: at yolo/poc **nobody was watching** - every decision the pipeline made alone (assumptions, auto-deferrals, blocker continuations) must surface here, loudly, or it never surfaces at all.

### 2.1 When and how - the completion sequence

The run **completes** when the last record of the resolved walk is `complete` (docs at mvp/prod; the loop's last stage at poc; implement at yolo - including a resumed run reaching that point, or a loop-halt resume exiting to docs). Then, in order:

1. **Write `00-Manifest/run-report.md`** from `templates/run-report.md`, assembled per § 2.2 - from artifacts only (pipeline.md, plan.md, findings.json, the code tree), never from subagent narratives.
2. **Update the manifest effort summary paragraph** in `00-Manifest/manifest.md` - **the conductor's ONLY manifest write, ever**: replace/write the one-paragraph effort summary (outcome, rigor, what shipped, residual counts, pointer to `run-report.md`). Stage lines stay untouched, as always.
3. **Completion notification** - the fourth and final trigger of `loop-and-budget.md` § 4, its mechanics and example line.
4. **Deliver the report as the closing message** - the full rendered report, not a pointer, as the final message of the turn (final messages are the one channel every host reliably renders; between-tool-call prose is not).

**HALTed runs get no report** - the halted `pipeline.md` is the state, and the HALT notification already carried the actionable fact; the report is written once, at completion (a resumed run writes it when it *reaches* completion). A re-invocation of a run that already completed announces it and points at the existing report (§ 1.1) - it never rewrites it.

### 2.2 Contents - section by section, each with its source of truth

| Section | Source of truth | Rules |
|---|---|---|
| **Header** | pipeline.md header + records | goal, rigor + source, **max + source, base** (the launch session; note `now <id>` when a resume ran inline stages on a different session model), outcome (`complete - N/N dispatches` or `complete with CONTINUE blockers`), links to pipeline.md + manifest.md. |
| **Stages run** | dispatch records + the artifact tree + the code tree | one row per dispatch record: stage · status · artifact link (canonical path, `references/artifact-structure.md`) · commits · spend. Commits are read from the code tree (`git log` on the run's branch - the worktree branch on `--worktree` runs) and attributed per stage via the stage's own artifacts (implement's `summary.md` per-phase commits; bugfix's `fix-summary.md`); `-` for stages that commit nothing. |
| **Assumptions** | `01-Plan/plan.md` § Assumptions | reproduced **VERBATIM - every row, unchanged, same columns** (`# · Question · Chosen answer · Why`, the plan-template shape). **The run report is this ledger's canonical reader** (contract row #6): an autonomous plan's self-answered questions surface here or nowhere. Interactive planning (no Assumptions section in the plan) → state `None - planning was interactive at this rigor; these calls were the user's.` An adopted plan (`--from-plan`) with no Assumptions section → `None - the plan was adopted from an existing deep-plan session; its calls were the user's.` |
| **Auto-deferred findings** | `findings.json` entries with `status: deferred` - **the source of truth**; the plan's Deferreds ledger is display-only derived state | **every** deferred finding, each with its **numeric severity** (+ tier as presentation): id · severity · one-line summary. Deferred ≠ rejected - nothing is ever auto-rejected. If findings.json and the plan's ledger disagree, report findings.json and note the drift. |
| **Residual open findings** | `findings.json` entries still `open` at completion | e.g. an mvp final re-review's fresh findings - never triaged **by design** (`loop-and-budget.md` § 1.4, cap 1); listed with severity and marked `open - never triaged`. Empty at clean convergence. |
| **Blockers** | pipeline.md Blockers table | reproduced whole: stage · **policy** (HALT/CONTINUE) · **report path** · note - every blocker, both classes, each with its report path. `None` when empty. |
| **Review loop** | pipeline.md Review loop table | the loop ledger reproduced - round · fresh CR ids · non-`fixed` count · certificate · decision (the Snapshot column stays in pipeline.md; it is plumbing, not outcome). Omit the section when the level ran no code review. |
| **Spend** | dispatch records' Spend (est) + the Spend running total; the Stage list's `Model` cells (write 2 - the model that actually ran) | per-stage + total, each stage with the **model that actually ran** (`<tier>: <id>`, fallbacks noted; inline stages `your session: <id>`; adopted plan `adopted - not run`), **always with the uncalibrated caveat** (heuristic bands per `rigor-levels.md` § Cost bands - estimates, never measurements). On `--budget` runs, the ceiling and the Budget events log ride along. |
| **Worktree** | pipeline.md header Worktree slot | **required whenever set** (`loop-and-budget.md` § 5): absolute path, branch, and merge instructions - review the branch, merge or PR it, then `git worktree remove <path>`; the conductor never deletes it. Omit the section when no worktree. |

The template (`templates/run-report.md`) carries this structure as fill-in slots; every value above is assembled at completion time - the template itself has no time-variant content.
